# 工程0: マインドセット

講座を開催する前に立ち戻る文書。工程1以降の設計判断は、すべてここから導かれる。

## 出発点

**「参加者にあまり響いていない」という感覚が、この講座の最も重要な材料である。**

これは失敗の記録ではない。ヒアリング記録10件（工程1）より先に手元にある、
唯一の一次データである。捨てずに扱う。

そして響かない理由の最有力候補は、講座が
**「参加者の苦痛から出発していなかった」**ことである。
生成AIの機能から出発した講座は、機能の紹介で終わる。
苦痛から出発した講座は、苦痛が減った実感で終わる。同じ内容でも着地が違う。

## テーマ

| 項目 | 内容 |
| --- | --- |
| 誰の | 学校現場の教職員 |
| 何を | 現場の苦痛 |
| どうする | 生成AIを通じて解消する |
| 結果として | Well-being につながる |

「生成AIを教える講座」ではない。**「苦痛を減らす講座で、手段が生成AI」**である。
この順序が逆になった瞬間、ユーザファーストは崩れる。

## 最大の逆風を先に認める

学校現場において、研修はしばしば**「また仕事が増えるもの」**として受け取られている。

参加者の多くは、学びに来た人ではなく**時間を取られた人**である。
これは参加者の意欲の問題ではなく、置かれた状況の問題である。

この前提を認めないまま設計すると、どれだけ内容が良くても
「良い話だったが、やることが増えた」で終わる。

したがって講座の最初の仕事は、教えることではない。
**「これは仕事を増やす時間ではない」と証明すること**である。

## 8つのマインドセット

### 1. 解決する前に、受け入れる

苦痛を聞いた瞬間に解決策を出さない。まず**その苦痛が存在することを認める**。

| 作り手の都合 | ユーザファースト |
| --- | --- |
| 「それはAIで解決できます」 | 「それ、しんどいですよね」を先に言う |

順序を逆にすると、参加者は「自分の苦労を軽く扱われた」と感じる。
そこから先はどんな解決策も入らない。受容は前置きではなく、機能である。

### 2. 「AIがすごい」ではなく「あなたの手が空く」

主語をAIから参加者に移す。

| 作り手の都合 | ユーザファースト |
| --- | --- |
| 「こんなことまでできます」 | 「この作業が、この時間で終わります」 |
| 最新機能のデモ | 参加者が明日やる業務での実演 |

「すごい」で終わった講座は、感心されて忘れられる。
参加者が受け取りたいのは驚きではなく、**返ってくる時間**である。

### 3. 最初に「仕事が減る」を証明する

冒頭で、参加者自身の業務が軽くなる場面を1つ、実際に見せる。
説明より先に、結果を見せる。

- 参加者が今週やる予定の作業を1つ選ぶ
- その場で短縮されるところまで見せる
- 「今日はこれを自分でできるようになって帰ります」と示す

ここを通過しないと、以降の内容は「増える仕事の話」として聞かれ続ける。

### 4. 現場の制約を否定しない

学校現場には現実の制約がある。個人情報を入力できない、自治体や設置者のルールがある、
端末や利用環境に制限がある、成績評価への利用に慎重さが求められる。

| 作り手の都合 | ユーザファースト |
| --- | --- |
| 制約を「まだ理解が追いついていない」と扱う | 制約を前提条件として設計に組み込む |
| 制約に触れず万能に見せる | 「これはできない」を先に明言する |

**制約を無視した講座は「うちでは使えない」の一言で終わる。**
できないことを先に言う講座のほうが信頼される。
そして「できない」の中に、参加者が一番不安に思っていることが含まれている。
そこに触れないのは、ユーザファーストではなく作り手の保身である。

ただし競合調査（2026-07-30）の結果、**制約の明言は差別化ではなく前提条件**であることが判明した。
文科省ガイドライン Ver.2.0 が個人情報・著作権の留意点を主体別に明示しており、
不安から入る研修（みんなのコード）も既に存在する。
守るべき作法ではあるが、これで選ばれるとは考えない。→ [competitors.md](competitors.md)

### 5. 参加者は「時間を取られた人」かもしれない

任意参加ではない研修では、参加者の初期状態が「前向き」であると想定しない。

- 冒頭で意欲を要求しない（「積極的に取り組みましょう」は要求である）
- 終了時刻を守る。延長は、それ自体が苦痛の追加である
- 持ち帰り課題を必須にしない（工程4⑥のとおり、本気の人向けは任意で用意する）
- 「使えるようになった人」だけでなく「使わない判断をした人」も否定しない

意欲は要求して生まれない。**苦痛が1つ減った実感から生まれる。**

### 6. Well-being は結論であって、入口ではない

Well-being は目指す地点として正しい。ただし**入口で掲げると精神論に聞こえる**。

現場が疲れているときに理念から入ると、「そんな余裕はない」と受け取られる。
入口は具体、出口が Well-being である。

```
入口: この集計作業が30分で終わる（お金／時間）
  ↓
中間: 持ち帰り仕事が減る、睡眠が戻る（健康）
  ↓
出口: 家族と過ごす時間、子どもと向き合う時間が戻る（人間関係）
  ↓
結果: Well-being
```

HARM（工程1）の主軸は**お金＝時間**に置く。そこから健康・人間関係へ接続する。
Well-being を最初に語らないことが、Well-being に届く道である。

### 7. 響かなかった感覚を、次の材料に戻す

「響いていない」で終わらせず、何が響かなかったのかを記録する。

- 参加者の表情が変わった瞬間／止まった瞬間
- 終了後に来た質問（→ [inputs/qa-log.md](inputs/qa-log.md) に原文で残す）
- 何も質問が来なかった回も記録する。**質問が出ないのは満足ではなく、接続していない兆候**である
- アンケートの自由記述は要約せず原文で保存する（→ [inputs/hearing-log.md](inputs/hearing-log.md)）

工程5のとおり、この循環が切れると講座は更新されなくなる。

### 8. 無料で手に入る内容に、参加者の時間を使わない

文科省は教員向け生成AI研修動画シリーズを**無料で公開**しており、
みんなのコードなどNPOも無料研修を開催している。
参加者が**すでにそれを見ている前提**で設計する。

| 講座から外す（無料で足りる） | 講座で扱う |
| --- | --- |
| 生成AIの仕組み・歴史・種類 | 参加者自身の業務での実演 |
| 一般的な注意点の列挙 | その業務が、その場で1つ終わること |
| 汎用的なプロンプト例の紹介 | 明日その参加者が使う具体的な手順 |

同じ内容を貴重な研修時間で繰り返せば、それ自体が「時間を取られた」体験になる。
**無料で手に入るものを出さないことが、参加者の時間を守ることである。**

これは競合調査で判明した最大の隙間（研修後の定着）と直結する。→ [competitors.md](competitors.md)

## 「響かない」を1つの原因に決めつけない

ユーザファースト不足は最有力候補だが、唯一の原因とは限らない。
次の回の前に、他の要因も点検する。原因を1つに決めると、そこだけ直して同じ結果になる。

| 要因 | 点検する問い | 該当したら |
| --- | --- | --- |
| 商品設計 | 参加者の苦痛から出発していたか | 工程1をやり直す |
| 参加の任意性 | 参加者は自分で選んで来たか | 冒頭で意欲を要求しない設計にする（5） |
| 時間帯・疲労 | 放課後・長期休業中など、すでに疲れている時間か | 内容量を減らす。延長しない |
| AIへの警戒 | 個人情報や利用ルールへの不安を抱えたまま聞いていたか | 制約を先に明言する（4） |
| 業務との接続 | 参加者自身の業務で実演したか、一般例だったか | 参加者の実業務に差し替える（2・3） |
| 既知の内容 | 文科省動画などで無料で得られる内容に時間を使っていないか | 該当部分を講座から外す（8） |
| 学校ごとの差 | セキュア環境の有無・校種・規模の違いを均していないか | 冒頭で確認し、実演を分岐させる |
| 立場の差 | 管理職と担任では苦痛が違うのに同じ内容を出していないか | 共通部分を絞り、残りを分岐させる |

**この表で該当が複数出たときは、商品設計だけを直しても響き方は変わらない。**

## 開催前の自己点検

- [ ] 参加者の苦痛を、参加者の言葉で1つ以上言えるか
- [ ] 冒頭で「仕事が減る」を証明する場面を用意したか（3）
- [ ] 「これはできない」を明言する箇所を用意したか（4）
- [ ] 参加者が明日やる業務で実演するか（一般例になっていないか）
- [ ] 冒頭で意欲を要求していないか（5）
- [ ] Well-being を入口に置いていないか（6）
- [ ] 無料で手に入る内容（仕組み・歴史・一般的注意点）を外したか（8）
- [ ] セキュア環境の有無で実演を分岐させる準備があるか
- [ ] 終了時刻を守れる分量か
- [ ] 終了後の質問を原文で記録する準備があるか（7）

## 開催後に必ずやること

1. 質問を原文のまま `inputs/qa-log.md` に転記する（要約しない）
2. 自由記述を原文のまま `inputs/hearing-log.md` に転記する
3. 響かなかった箇所を、上の「1つの原因に決めつけない」表で点検する
4. 同じ質問が3回来ていたら、それは教材の欠陥として直す（工程2）
