# 講座設計プロセス — ユーザファースト

講座を「作りたいもの」から作り始めない。**受講生がすでに口にしている言葉**から逆算して作る。
このディレクトリは、その手順を再現可能な形にしたものである。

## 貫かれている一つの原則

すべての工程で、判断基準を**作り手の都合から受講生の都合に置き換える**。

| 工程 | 作り手の都合（避ける） | 受講生の都合（採る） |
| --- | --- | --- |
| コンセプト | 自分が語れること | 顧客が悩みとして口にした言葉 |
| カリキュラム | 自分が教えたい順 | 受講生がつまずく順 |
| 台本 | 網羅的な正しさ | 声に出して違和感がないこと |
| 特典 | 数の多さ | メイン商品の弱点を埋めること |
| 仕上げ | AIの出力で完成 | 最後の5%に人間の体験を入れる |

この表に反する判断をしたときは、必ず理由を書き残す。

## 講座のテーマ

**学校現場の苦痛を、生成AIを通じて解消する。結果として Well-being につながる。**

| 項目 | 内容 |
| --- | --- |
| ターゲット | 広く学校現場の人（絞らない方針として確定） |
| 苦痛の領域 | 学校現場の業務負担 |
| 手段 | 生成AI |
| HARM主軸 | お金＝時間（→ 健康 → 人間関係へ接続） |
| 到達点 | Well-being |

「生成AIを教える講座」ではなく「苦痛を減らす講座で、手段が生成AI」である。
詳細は [00-mindset.md](00-mindset.md)。

リポジトリ名の学校評価（`gakkouhyouka`）および `dashboard` のHTMLプロトタイプは
この講座とは別テーマのため、設計の参照元にしない。

### 競合の隙間（調査済み）

軸は **研修後の定着（出口）**。参加者自身の業務が、その場で1つ終わること。

制約の明言（個人情報・ルール）は差別化ではなく**前提条件**である。
文科省ガイドラインが既に明示しており、苦痛・不安から入る研修も既に存在する。
→ 詳細と根拠は [competitors.md](competitors.md)

## 進め方

1. `inputs/` を埋める（人間の作業）
2. 工程1〜2をAIと対話しながら確定させる（`01-concept.md` / `02-curriculum.md` の各プロンプトを使う）
3. 工程3で台本を量産する
4. 工程4で特典を6基準で絞る
5. 工程5で最後の5%を人間が入れる
